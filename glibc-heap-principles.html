glibc 堆破坏延迟暴露：原理图解

从 chunk 元数据到 core dump：为什么「问题发生时刻」不等于「core 产生时刻」

定性一 · 被动 / 局部 / 调用点堆检查只在 _int_malloc / _int_free 执行时发生，只校验当前 chunk 及其直接邻居。无后台扫描，无定时体检。
定性二 · 依据在元数据里判断依据全部存放在 chunk 自身的 size / prev_size / next / key。被正常业务写入覆盖后，检测条件不再成立。
定性三 · core 是终止瞬间快照core 为 ELF 格式（PT_LOAD + PT_NOTE），只含进程死亡瞬间的内存与寄存器，不含任何历史执行轨迹。
一句话总原理：glibc 只登记 chunk 状态，不维护「指针 → 持有者」的映射。因此「chunk 已释放但旧指针仍被持有」这件事，从原理上不可判定；而检查又只在下一次堆操作调用点发生，于是破坏可以静默任意久，直到某次 malloc/free 命中它才 abort。

01两个时刻：现象与真实机制

故障现象是「进程退出时 core dump，原因是 double free，但实际破坏发生在退出前一段时间」。这个现象成立，而且对堆破坏类故障是常态（fail-late），不是特例。需要修正的是对机制的解释。

两个常见误判：①「glibc 是抽查式检查，刚好没发现」——检查是确定性的、发生在每次调用点，不存在抽查；②「进程退出时 glibc 做全量检查才发现」——exit() 不遍历 arena / bin / chunk，内核直接回收地址空间，不存在全量一致性校验。
图 1 · 破坏发生在 T2，报错发生在 exit 阶段；两者之间只要没有堆操作触碰该 chunk，就没有任何检查发生。

速览先看流程：一块内存的六帧分镜

前面各章给的是结构图和名词表；这一章把它们拼成一条连续的时间线——只跟踪同一块内存，从它被申请到进程 abort，走完 6 个瞬间，每帧只变一处。先看懂这条线，后面的术语只是给这些格子贴名字。

全程只有 3 个角色，并且有一个必须记住的前提：p 与 q 的数值完全相同（同一个地址）。组件 A 释放后留下的旧指针 p，与业务 B 后来拿到的指针 q，指向的是同一块内存。
角色它做什么 / 不做什么
组件 A最初使用这块内存；动作完成后 free(p)，但没有把 p 置空，于是留下悬垂指针。
业务 B后来做哈希，申请同 size 内存，拿到 q（q == p），往里写哈希数据。
glibc只维护两件事：这块 chunk 是「已分配」还是「空闲」、挂在哪个 bin 上。不记录这个地址发给过谁。

图 A · 六帧：每帧只变一处

图 A · 六帧分镜。请重点看每帧底部三行：A、B、glibc 三者的记录从 T4 起不再一致，而 glibc 自己看不到这个不一致。

逐帧只说「这一帧变了什么」

T0 → T1　A 调 free(p)glibc 没有清空内存，只在用户区开头写了 next / key，把 chunk 挂进 tcache 空闲链。p 的值没变，A 手里还攥着它 —— 这就是悬垂指针。
T1 → T2　B 要同 size 内存tcache 按大小分栏且后进先出，链头正是这块，必然发给 B（q == p）。取出时 tcache_get 顺手把 key 清成 NULL。
T2 → T3　B 写入哈希数据一次完全正常的业务写入，覆盖了用户区开头 16 字节，key 从此不再是 tcache。此刻 p 和 q 同时指向这块内存。
T3 → T4　A 用旧指针 free(p)真正的破坏点。glibc 把这块又挂回 tcache，但 B 还在用它。全部检查项都通过，本次调用没有任何报错。
T4 → T5　状态错位glibc 的记录是「空闲」，实际 B 在使用。这个错位就是全部问题；它不会自己浮现，直到某次堆操作命中它。
T5 → exit　踩雷退出阶段集中执行析构、单例释放、缓冲区刷出等大量 free()，堆操作密度最高，撞上这页乱账 → abort() → core。

图 B · T4 为什么没被拦住：把那一刻的检查逐项摊开

图 B · 不是「抽查漏掉」：前四项本来就该通过，第五项是唯一能抓重复释放的条件，而它的前提已被正常流程清掉。没有判定条件，不是运气。

图 C · 破坏点（T4）与报错点（exit）之间可以任意长；退出阶段不是「检查」，是堆操作最密集所以最容易踩雷。

三个最容易卡住的点

卡点答案
释放了为什么还能再释放free 不清空内存，也不改动 p 的值；glibc 只登记 chunk 状态，不记录「这个地址发给过谁」。
为什么当时没报错唯一的去重检查依赖 key。T2 被 tcache_get 清成 NULL、T3 被 B 的数据覆盖，检查前提不成立；而且检查只发生在这一次调用点，过了就过了。
为什么拖到退出才炸静默期没有 malloc/free 触碰这块 chunk = 没有任何校验；exit handlers 里密集的 free 命中它 → abort() → core 是那一瞬间的快照，自然没有 T4 的调用栈。
整条线只有一句话：同一块内存被 glibc 登记为「空闲」，却仍被业务 B 使用，而 glibc 没有任何信息能发现这个错位，直到退出阶段某次堆操作撞上它。所以 AI 那两句——「glibc 抽查式，刚好没发现」是根本没有判定条件，「退出时全量检查才发现」是根本没有全量检查这回事；现象链条本身完全成立。

02名词地图

按层次分组。后文所有机制描述都只用这些术语。

A · 基础

名词含义
glibcGNU C Library，用户态 C 运行时。malloc/free 由它实现，不是内核系统调用。
malloc / free用户态接口，内部入口 __libc_malloc / __libc_free，实际逻辑在 _int_malloc / _int_free。
heap / arenaheap 为进程地址空间中由 brk/mmap 获得的可写区；arena 是管理一个 heap 的结构，主线程对应 main_arena，非主 arena 由 NON_MAIN_ARENA 标志标识。
指针malloc 返回的地址，即 chunk 用户区起点 mem。它只是地址值，不含所有权、生命周期或引用计数信息。
悬垂指针 / UAFchunk 已 free 但指针值仍被保存，后续被解引用或再次传给 free，即 use-after-free。
double free两种语义：① 同一指针连续 free 两次且中间未重新分配；② chunk 已 free 并被重新分配后，旧指针再 free 一次（严格说是 UAF 导致的 stale-pointer free）。二者可检测性完全不同。

B · chunk 结构

名词含义
chunk堆分配的最小单位，64 位下按 16 字节对齐。
prev_size头部第一个 8 字节字段。仅当前一个 chunk 空闲时有效；物理上复用前一 chunk 用户区末尾 8 字节。
size头部第二个 8 字节字段，记录本 chunk 总大小（含头部），低 3 位借作标志位。
PREV_INUSE / IS_MMAPPED / NON_MAIN_ARENAsize 的 bit0/1/2：前一 chunk 是否使用中、是否 mmap 单独分配、是否属非主 arena。读大小需先掩码。
mem用户可用区起点，mem = chunk + 16，即 malloc 返回值。
MINSIZEchunk 最小尺寸，64 位下 0x20：16 字节头 + 至少 16 字节用户区（容纳两个指针）。
tcache_entrychunk 放入 tcache 时，mem 起始 16 字节被 reinterpret 为 { struct tcache_entry *next; uintptr_t key; }。

C · bin 体系

名词含义
bin按大小分档的空闲 chunk 链表集合，用于复用已释放内存。
tcache2.26 引入，每线程私有（tcache_perthread_struct），64 个 size class 的单向 LIFO 链，默认每 bin 容量 7（tcache_count）。不检查相邻 chunk、不做 coalescing，是最快路径。
size class按 chunk 大小分档，相邻档间隔 16 字节；同档请求命中同一条链。
next / keynext 指向该 bin 中下一个空闲 chunk；key 写入 tcache 结构自身地址，2.29 起用作 double free 检测标记。
countstcache_perthread_struct 中记录各 bin 当前 chunk 数的数组。
fastbin小尺寸 chunk（默认上限 DEFAULT_MXFAST，64 位下 0x80）的单向 LIFO 链。free 时不清除下一 chunk 的 PREV_INUSE，故不合并。
unsorted / small / large bin双向循环链。unsorted 暂存刚释放的 chunk，遍历时按大小分流；large bin 内按大小排序做最佳适配。
top chunkarena 末端未分配的连续区；不足时由 sysmalloc 通过 brk/mmap 扩展。
safe-linking2.32 起对 next 编码 PROTECT_PTR(pos,ptr) = (pos >> 12) ^ ptr，取出时 REVEAL_PTR 解码；结果未对齐即报 unaligned tcache chunk detected。
unlink / coalescing从双向链摘除 chunk（校验 fd->bk == p && bk->fd == p）；coalescing 为前后相邻空闲 chunk 合并。

D · 函数与路径

名词含义
_int_malloc / _int_free分配 / 释放的内部实现，所有检查逻辑都在这两个函数内。
tcache_get / tcache_put从链头取 / 放 chunk。tcache_get 会执行 e->key = NULL；tcache_put 写 next、key = tcache 并递增 counts。
malloc_consolidate把 fastbin 中的 chunk 合并并移入 unsorted bin（大请求或 top 不足时触发）。
sysmalloctop chunk 不足时向内核扩展 arena。
malloc_printerr检测到不一致时的统一报错入口，调用 __libc_message 输出错误串后 abort()。

报错串触发条件

F · 进程终止与 core

名词含义
exit() / __run_exit_handlers执行 atexit/on_exit 回调、__cxa_finalize（C++ 全局/静态对象析构）、stdio flush，最后进入 _exit。
_exit / exit_group系统调用，内核销毁 mm_struct、回收页表与物理页。malloc 的 arena/bin/chunk 元数据不被遍历、不做一致性校验。

do_coredump()内核生成 core 的函数，受 RLIMIT_CORE、/proc/sys/kernel/core_pattern 控制，页面范围受 coredump_filter 过滤。
ELF core / PT_LOAD / PT_NOTEcore 文件格式。PT_LOAD 保存被选中的内存页；PT_NOTE 保存 NT_PRSTATUS（各线程寄存器）、NT_PRPSINFO、NT_AUXV、NT_FILE（映射表）等。
MALLOC_CHECK_ / GLIBC_TUNABLES环境变量形式的 malloc 行为开关；2.34 起 MALLOC_CHECK_ 由 glibc.malloc.check tunable 取代。

03chunk 与元数据：free 究竟改写了什么

64 位下 chunk 按 16 字节对齐，头部 16 字节为 prev_size 与 size。mem = chunk + 16 是 malloc 返回值。size 低 3 位为标志位，读取大小前必须掩码。prev_size 仅在前一 chunk 空闲时有效，且物理上位于前一 chunk 用户区末尾 8 字节——这是 chunk 之间的重叠复用设计。

关键点：free() 不清零内存，也不修改调用方持有的指针值。它把 mem 起始 16 字节 reinterpret 成 tcache_entry，写入 next 与 key，并把 chunk 挂入对应 bin。因此「释放后指针仍被持有」是接口语义的直接结果，不需要任何异常代码路径。
图 3 · 同一块内存的两种解释。检测所依赖的 key 位于用户可写区，这是第 5、7 节能否检测的分水岭。

04bin 体系、分配 / 释放路径与检查点

_int_malloc 顺序：tcache（size 落在范围内且 counts < tcache_count）→ fastbin → smallbin 精确匹配 → unsorted bin 遍历分流 → largebin 最佳适配 → top chunk → sysmalloc。tcache 取链头即可返回，不读取相邻 chunk、不触发 malloc_consolidate、不做 coalescing，是校验最少的一条路径。

_int_free 顺序：基础校验（指针对齐 / 地址范围、size >= MINSIZE 且对齐、nextchunk->size 合法）→ size 落在 tcache 范围且 bin 未满则 tcache_put 后直接返回 → 否则 fastbin 链头插入 → 否则前后相邻空闲合并、unlink、放入 unsorted bin（IS_MMAPPED 的 chunk 走 munmap）。

同 size 请求必然命中刚释放的 chunk：tcache 按 size class 分 bin、链头插入链头取出（LIFO），刚 tcache_put 的 chunk 就在 entries[tc_idx]，下一次同档 _int_malloc 第一个取到它。这是链表结构决定的，不是概率事件。

图 4 · 检查点分布。红色框是唯一针对「重复释放」的检测，成立条件在第 5 节展开；图中为短名，各检查项的完整报错串见第 2 节 E 组。

05tcache 的 double free 检测机制（2.29 起）

/* tcache_put，简化 */
tcache_entry *e = (tcache_entry *) chunk2mem(chunk);
if (e->key == tcache) {                      /* 检测分支的唯一入口条件 */
    for (tmp = tcache->entries[tc_idx]; tmp; tmp = REVEAL_PTR(tmp->next))
        if (tmp == e)
            malloc_printerr("free(): double free detected in tcache 2");
}
e->next = PROTECT_PTR(&e->next, tcache->entries[tc_idx]);
e->key  = tcache;                            /* 写入检测标记 */
tcache->entries[tc_idx] = e;
++tcache->counts[tc_idx];

/* tcache_get，简化 */
tcache_entry *e = tcache->entries[tc_idx];
tcache->entries[tc_idx] = REVEAL_PTR(e->next);
--tcache->counts[tc_idx];
e->key = NULL;                               /* 关键：标记被清除 */
return (void *) e;

PROTECT_PTR / REVEAL_PTR 是 2.32 起的 safe-linking 编码 ((uintptr_t)pos >> 12) ^ ptr，早期版本直接赋值 e->next。要点是：整个检测都以 e->key == tcache 为前提，而 key 位于 mem 起始 8 字节，属于用户可用区。

图 5 · key 的状态迁移。tcache_get 主动清 NULL 加上业务写入覆盖，共同造成情形 B 不可检测。

06检查机制的三大性质

维度具体事实
被动仅在执行 _int_malloc / _int_free 的调用点检查。glibc 无后台线程、无定时扫描、无 arena 遍历。
局部只校验当前 chunk 的 size / prev_size、所在 bin 的链头、unlink 时的 fd/bk 互指关系、top chunk size。fastbin 的 double free 检测甚至只比对链头一个元素。
元数据依赖判断依据全部来自 chunk 自身字段。业务对 mem 的正常写入会覆盖这些字段。
不一致时malloc_printerr → __libc_message 输出错误串 → abort()。
推论：从元数据被破坏到下一次触碰该 chunk 的堆操作之间，不存在任何校验动作。静默任意长都不会报错，这是制度性行为，不是偶然。
图 6 · 三条性质是判断任何类似结论真伪的稳定判据。

07两种 double free：可检测性差异

A · 同一指针连续 free 两次B · free → 重新分配 → 悬垂指针再 free
e->key 状态仍等于 tcache（tcache_put 刚写入）tcache_get 已置 NULL，且被业务写入覆盖
检测分支进入，遍历 bin 命中同一 chunk → 报错不进入，e->key == tcache 不成立
其余校验—指针合法、size 合法、bin 未满 → 全部通过，执行 tcache_put
结果当场 abort放行；chunk 同时被 bin 标记为空闲、又被业务持有
根本原因：glibc 的 bookkeeping 只维护 chunk 状态（inuse / free）与 bin 归属，不存在「指针值 → 持有者 / 所有权」的映射。判断一次 free(p) 是否合法，等价于判断 p 是否为当前有效分配的 owner；该信息属于程序语义，malloc 无法获取。情形 B 不是「检测漏过」，而是不存在可判定条件。

后续如何才最终 abort：该 chunk 既在 bin 中又在业务手里，之后要么业务再 free 一次使同一 chunk 重复入链（下一次 tcache_put / tcache_get 的字段校验失败），要么被再次分配给第三方造成两个持有者互相写坏 size / prev_size（触发 corrupted size vs. prev_size 或 malloc(): memory corruption (fast)）。直到那一次调用点，malloc_printerr 才执行。

图 7 · 差别只在 key 是否完好。属于元数据层面的可判定性差异，不是检查强度或抽样率差异。

08延迟暴露的完整因果链

  1. free(p) → tcache_put 写 next / key；调用方仍持有 p（悬垂指针）。
  2. 同 size _int_malloc 走 tcache_get：e->key = NULL，业务写入覆盖 mem 前 16 字节。
  3. 悬垂指针再次 free(p)：e->key != tcache，检测分支跳过，tcache_put 成功。
  4. chunk 状态不一致（bin 记为空闲、业务仍持有），但此刻所有校验均通过，无报错。
  5. 静默期：无 _int_malloc / _int_free 触碰该 chunk，故无任何校验发生。
  6. exit handlers 中的 free() 或其他堆操作命中不一致 → 字段校验失败。
  7. malloc_printerr → abort() → SIGABRT → core。
图 8 · 「延迟 N 分钟」在机制上成立，但时长本身无法从 core 反推（见第 11 节）。

09进程退出、abort 与 core

exit() → __run_exit_handlers（atexit/on_exit 回调、__cxa_finalize 触发 C++ 全局与静态对象析构、stdio flush、动态库卸载）→ _exit/exit_group → 内核销毁 mm_struct 并回收页表与物理页。malloc 的 arena / bin / chunk 元数据在此过程中不被遍历，也不做任何一致性校验。

但 exit handlers 内部包含大量普通 free() 调用，这些调用会正常进入 _int_free 并执行第 4 节的检查点。所以退出阶段报错的原因是该阶段堆操作密度最高、恰好触碰到此前被破坏的 chunk，不是 glibc 在退出时做了额外校验。

abort() → raise(SIGABRT)，信号 6 默认动作 terminate + core → 内核 do_coredump()，受 RLIMIT_CORE、core_pattern、coredump_filter 控制，产出 ELF core：PT_LOAD 保存被选中的内存页，PT_NOTE 保存 NT_PRSTATUS（各线程寄存器）、NT_PRPSINFO、NT_AUXV、NT_FILE（映射表）。

core 中不存在历史执行轨迹。已返回的调用帧没有可靠的帧链记录，破坏时刻那次 free 的调用者、调用栈、参数均不在任何 PT_LOAD / PT_NOTE 结构中。因此「core 不是问题发生时刻」由 core 的数据格式决定，与运气无关。

10用原理逐句核 AI 的五句结论

AI 结论判定依据判定修正 / 说明
① 组件释放后仍持有指针free 不修改调用方指针值成立悬垂指针 / UAF 起点
② 同大小内存「刚好」分配给哈希tcache 按 size class 分 bin、LIFO 链头取放事实成立非概率事件，是链表结构决定的必然
③ 只释放了一部分_int_free 以整个 chunk 为单位，不存在部分释放不成立可成立的表述：tcache_put 改写 mem 前 16 字节，而哈希在此之前已完成读取，或输入范围不含该区域
④ glibc 抽查式，刚好没发现检查在调用点确定性执行；情形 B 中 e->key 已被清除 / 覆盖，检测分支不成立不成立既非抽查，也非漏检，是无判定条件
⑤ 退出时 glibc 全量检查才发现_exit 不遍历 arena / bin，无一致性校验不成立退出阶段报错源于 exit handlers 内的 _int_free 命中被破坏的 chunk
补充：core 不是问题发生时刻core 仅含终止瞬间的 PT_LOAD / PT_NOTE成立由数据格式决定，且为必然
总体评价：现象链条（UAF → 同 size 复用 → 悬垂指针二次释放 → 静默 → 退出阶段 abort）在机制上完全能成立；讲错的是「抽查」与「退出全量检查」两个机制名词，以及「只释放了一部分」这个不符合接口语义的表述。

11证据边界：哪些结论不能从 core 反推

这一节是「能加得上账」的约束：core 里没有的，就不能当作已证实事实写入复盘。

项为什么推不出处理
「静默 N 分钟」的具体时长core 只有终止瞬间状态，无时间线上的事件记录只能来自业务日志 / 时序记录；无外部证据则标注为估计或待证
「只释放了一部分」_int_free 以 chunk 为单位；core 中无该次调用的过程信息无 ASan / valgrind 类报告支撑，属推测，应删除
「哈希正常完成」tcache_put 会改写 mem 前 16 字节有条件成立：读取发生在改写之前，或输入范围不含该区域；否则与被 free 相矛盾，需回查
「glibc 全量检查」机制不存在删除
破坏时刻的调用者 / 调用栈已返回的帧没有可靠帧链记录core 中无法获得；core 里的栈属于触发 abort 的那次调用

12版本差异（按现场 glibc 版本核对）

「能不能当场抓到」必须带上版本号说；但第 6 节的三条性质与「exit 不检查堆 / core 无历史」与版本无关。
