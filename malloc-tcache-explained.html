内存分配器是怎么工作的

chunk、bin 与 tcache：从一次 malloc 到一次 free，正面讲清分配器的机制

01分配器要解决的三个问题

抛开所有名词，glibc 面对的堆就是一大段连续字节。程序不断提出要求：给我 24 字节、给我 100 字节、这块我不用了……分配器必须回答三个问题。后面所有设计都是为了回答它们。

图 1 · 三个问题对应三种机制。tcache 不是另一套内存，而是"从空闲链表里切出来的一小段快速通道"。

02malloc 的完整路径

调用 malloc(n) 后，glibc 先把 n 换算成 chunk 大小，然后从最快的通道开始一路往下找，直到拿到一块内存。绝大多数小请求在第 1 站就返回了；只有缓存空了才往下走。

图 2 · malloc 查找顺序。前四站都在用户态操作空闲链表，只有最后一站进内核。你要理解 double free，只需盯住第 ① 站。

03free 的完整路径

free(p) 做的事，本质是把 p 对应的 chunk 挂回空闲体系。它会先做一组基础校验，然后优先塞进 tcache——只要该档没满。这一步就是 tcache_put，也是整个机制里最关键的函数。

图 3 · free 路径。重点看 tcache_put 那一步：它把 next/key 写进用户区前 16 字节——这正是下一节实例里反复发生的事。

05chunk：一块内存的真实样貌

堆里的每块内存都叫 chunk。它在用户数据前面藏了 16 字节的头（64 位下两个 8 字节字段）。malloc 返回的 mem 是用户区起始地址，比 chunk 起始地址大 16。你的代码只能看到用户区，头是 glibc 的记账区。

图 5 · chunk 结构。size 的高位存大小、低三位存状态；头这一部分属于 glibc，越界写前 16 字节就会破坏记账信息。

06chunk 头两字段：prev_size 与 size 到底干什么

先纠正一个常见说法：头 16 字节不是"两个 size"，而是 prev_size（8B）和 size（8B），两者分工完全不同。它们配合实现 glibc 的边界标记（boundary tag）机制——让 free 时能 O(1) 找到相邻块并合并。

prev_size 的反直觉点：前块在用时不归本块

只有前一块空闲（P=0）时，prev_size 才存着前一块的大小，glibc 才能算出前块起点、把它从 bin 摘下来合并。前一块正在使用（P=1）时，这 8 字节被前一块借去当用户数据——这正是源码注释里的 "size of chunk, but used for application data"（malloc.c:1194），也是 malloc_usable_size() 常比你请求的多 8 字节的原因之一。

还有个容易混的点（malloc.c:1247）：本块的 footer 其实就是"下一块的 prev_size 字段"。空闲块的大小在块头 size 和下一块 prev_size 各存一份，正是这份冗余让向前、向后两个方向的合并都能 O(1) 完成——这就是"边界标记"名字的由来。

连回 double free 场景

埋雷块 P 进哪个 fastbin、B 为什么能从 fastbin 取回同一个 P，都由 P 的 size 决定。而 fasttop 检查只比链头地址 old == p，不读 size、不读 prev_size，所以这两个字段在你的主线里不是检测点，只是"块能被这样调度"的前提。core 里看到的 size 是崩溃那一刻的值；B 写用户区只覆盖前 16B 的用户字段位，不会动头里的 size，所以 size 通常仍可信，能反推块的档位。

07空闲块怎么记账：size class 与 bin

光有 chunk 还不够，glibc 必须知道"哪些块空着"。做法是按大小分档管理空闲块：小尺寸按 32 字节一档、48 字节一档、64 字节一档（每档 +16B）……每一档维护一条链表，统称 bin；大块（large bin）则改用分组递增的档宽。这样请求 24 字节时，直接去"32 字节档"的链表找即可，不用遍历整个堆。各容器具体有几档，见本章末尾的对照表。

图 8 · 分档 + 链表 = 快速定位空闲块。请求 24 字节只会去 0x20 档的链上看，不会翻遍整个堆。
size class
按 chunk 大小分的档位，相邻档差 16 字节。请求先算出 chunk 大小，再映射到对应档。
bin
同一档空闲块的链表集合。glibc 有多类 bin：tcache、fastbin、smallbin、largebin、unsorted bin。
next
空闲块用户区前 8 字节的字段，指向同档的下一个空闲块。把空闲块自己变成链表节点。

08tcache：为什么它最快

tcache（thread cache，线程缓存）是 2.26 引入的一层"快速通道"。它不是一个独立的堆，而是从空闲块体系里切出来的一小段缓存，特点是每线程私有（不用加锁）、按大小分 64 档、每档最多 7 个块、链头进出。malloc 和 free 都先看它。

图 9 · tcache 结构。记住下一节会用的一条：每档 7 个上限、链头进出、key 标记。
为什么"链头进出"是必然复用的关键：你 free 掉的块会被放到对应档的链头；紧接着同档的 malloc 一定先取链头。所以"刚释放的同大小内存马上又分给下一次请求"不是巧合，是数据结构决定的。

09tcache 与各类 bin 的关系

tcache 不是 bin 之一，而是 bin 体系前面的拦截层。free 和 malloc 都要先过 tcache：命中就立即返回，完全不碰下面的 bin；没命中才下探到后端。各类 bin 是 tcache 之外的全部复用手段，两者是前后两级，不是并列关系。

图 10 · tcache 是拦截层，bin 是后端。每次 free / malloc 都先过 tcache，命中即返回。

free(p)：尺寸在 tcache 范围内且该档没满（默认 7 块）→ 写 next/key 存入 tcache 并立即返回，不会进 fastbin 或 unsorted bin；档位满了或尺寸太大才落到后端。malloc(n)：同档 tcache 非空 → 取链头立即返回；链空了才按 fastbin → small → unsorted → large → top → sysmalloc 一路找下去。

后端各容器分工不同：fastbin 管最小块（单链 LIFO、不合并）；small bin 按精确尺寸分档（双向链）；unsorted bin 是刚释放块的分拣过渡站，下次 malloc 时把块分流到 small/large 或直接使用；large bin 按尺寸范围分档、内部排序；top chunk 是堆尾剩余空间，都不够才向内核扩堆。

10next / key 到底写了什么，key 有什么用

你的理解"free 后在用户数据区写 next 和 key，next 指向下一块空闲内存，块挂在 tcache 或各类 bin 下且互斥"——方向对，但有三处要收紧。

图 12 · 只有 tcache 写 next + key；fastbin 只有 fd；双向 bin 写 fd + bk。
  1. next / key 不是"释放登记表"。它们是空闲链表节点本身——glibc 不另建账本，块自己就是节点。真正额外的标记只有 key。
  2. "下一块"指同一条空闲链表上的下一块（同 size class），不是物理地址相邻的块；双向 bin 里是 fd/bk 两个方向。
  3. 互斥只在某一瞬间成立。块会随时间流动：tcache 满 → 落到 bin；从 bin 被 malloc 取走 → 变成已分配；再 free → 又回 tcache。合并路径下原块还会被并入更大的块。

key 的作用：不是检查本身，是"要不要检查"的开关

tcache 是单链，要判断"这块是不是已经在链上"本来得遍历整条 bin（O(n)），每次 free 都遍历太慢。2.29 起加入 key：块进 tcache 时写入本线程 tcache 结构的地址作为"盖章"，于是 tcache_put 可以先用 O(1) 判断：

条件glibc 的动作代价
e->key != tcache视为正常情况，直接挂链，不遍历O(1)
e->key == tcache可疑：遍历该档链表查重，发现同一块已在链上就报 double free detected in tcache 2 → abortO(n)，但极少发生
你的场景为什么进不了这个分支：tcache_get 取走块时把 key 清成 NULL，随后业务写入覆盖这一格。旧指针再次 free 时 key 已不是 tcache → 连查重分支都不进，直接放行。key 只存在于 tcache；fastbin 靠比链头，双向 bin 靠 fd/bk 互指校验——同一类错误落在不同层，检测能力不同。

11key 与重复释放检测

现在可以回答：glibc 到底靠什么发现"重复释放"。答案只有一个字段——key。它在 tcache_put 时被写成 tcache 自身地址，在 tcache_get 时被清成 NULL。只有当一个块还躺在 tcache 里、key 完好时，检测才成立。

图 13 · key 是唯一线索。B 型（free → 重新分配 → 旧指针再 free）中 key 已被撕掉或被业务数据覆盖，检测分支不成立——这是能力边界，不是抽查漏检。详见故障分析手册。
和你的问题的接口：你的场景正是 B 型。component A 释放后留着旧指针 p；同大小内存被 malloc 给哈希业务（p 与新指针同址）；哈希写入覆盖了 next/key；A 再用 p 调 free 时，key 已不是 tcache，检测跳过。之后某次堆操作撞上不一致的链才 abort。

12brk / mmap 分界线与 tcache / bin 的关系

这是两个不同层次的问题：brk / mmap 决定内存从哪来，tcache / bin 决定拿到的块怎么复用。你讨论的 next/key/double free，全部发生在前一条路线上。

图 14 · brk/mmap 是"内存从哪来"，处在 tcache/bin 的上游；mmap 大块不参与空闲链表复用。
  1. malloc 先查 tcache、再看 bin，最后才看 top chunk；只有 top chunk 也不够、需要调 sysmalloc 向内核扩堆时，才按 mmap_threshold 分流。
  2. 请求小于阈值 → brk 扩展主 arena 的堆（非主 arena 用 mmap 划出一大片 arena 区域），切出的块照常进 tcache/bin 体系。
  3. 请求大于等于阈值 → 单独 mmap 一块，size 标 IS_MMAPPED；free 时直接 munmap 归还内核，不进 tcache、不进任何 bin。因此 double free 那套链条只发生在 arena 块上。
精确性提醒：默认阈值约 128 KB，可通过 M_MMAP_THRESHOLD / MALLOC_MMAP_THRESHOLD_ / glibc.malloc.mmap_threshold 调整，且 glibc 会动态改变它；阈值判断只发生在 top 不够时——即使请求超过阈值，top chunk 够大仍可能直接从 top 切。具体值按现场 glibc 版本核对。

13malloc 完整路径：从 request2size 到 brk / mmap

前面第 2 章给的是"查找顺序概览"，第 12 章给了分界线。这一节把两端补齐：先给出 request2size 的精确换算，再把 s5 最后那站 sysmalloc 完全展开——看清楚 mmap 阈值判断、brk 扩展、以及非主 arena 的 grow_heap / new_heap 各自在什么位置。以下分支对应 glibc 2.35 源码。

第 0 步：request2size — 把 n 换算成 chunk 大小

你调用 malloc(n) 里的 n，不是 chunk 的 size。glibc 先补上 size 字段、再按 16 字节对齐，并设一个下限。源码 1331 行的宏：

#define request2size(req) \
  (((req) + SIZE_SZ + MALLOC_ALIGN_MASK < MINSIZE) \
   ? MINSIZE \
   : ((req) + SIZE_SZ + MALLOC_ALIGN_MASK) & ~MALLOC_ALIGN_MASK)
/* 64 位：SIZE_SZ=8, MALLOC_ALIGNMENT=16, MALLOC_ALIGN_MASK=15, MINSIZE=32 */
请求 nn + 8向上对齐到 16chunk size用户区可用
malloc(1)916 < MINSIZE32（取下限）24 字节

为什么 +8：malloc 返回的是用户区起点（mem），它前面还有 8 字节的 size 头。所以 nb = align16(n + 8)，向下多算的这点空间就是给元数据用的；prev_size 那一格只在块空闲时才被借用，分配中归前一块使用。

与本主题的关系double free / fasttop / key 全部发生在这条路不参与空闲链表，也不产生 fasttop 报错
两个容易记错的点：① mmap 阈值默认 128 KB，但它是动态的——释放一个 mmap 块时 glibc 可能把阈值抬到该块大小（源码 3373–3379 行），也能用 M_MMAP_THRESHOLD / MALLOC_MMAP_THRESHOLD_ 固定。② 阈值判断只在 sysmalloc 里做，也就是 top chunk 不够时；即使请求超过 128 KB，只要 top 够大，仍可能直接从 top 切，不走 mmap。

这样，从你写下的 malloc(n) 到拿回指针，中间经过的每一站、以及 brk 和 mmap 各自在哪一步被触发，就都串起来了。前面 s4–s8 讨论的 next/key/double free，全部落在补图 D1 中"arena 路径"这条支线上——这也是为什么 fasttop 报错只可能来自小块、且一定在 arena 分配出来的 chunk 上。

15常见误解澄清

容易以为实际是
free 会把内存清零不清零。只改 chunk 头和那 16 字节元数据，旧数据还在。所以 UAF 能读到脏数据。
free 后指针会自动失效 / 变 NULL不会。C 里指针只是整数值，free 不改它。需要你手动置 NULL。
chunk 大小 = 请求大小chunk = 对齐(请求 + 8, 16)，还含 16 字节头。请求 24 → chunk 32。
tcache 是另一块独立内存不是。它只是把空闲块按档缓存起来，块仍来自同一个堆。
"同大小刚好又分给它"是巧合是 size class + LIFO 链头的必然结果。刚释放的块就在链头，下次同档请求第一个取到它。
glibc 会抽查 / 定期体检发现坏块不会。检查只在 malloc/free 调用点、针对当前操作的那块发生，没有后台扫描。
key 被覆盖是"运气不好"是机制必然：块重新分配后业务写入用户区，必然覆盖同址的 next/key。
收束：分配器的核心就是"把块切成 chunk、用 next 把空闲块串成链、用 tcache 加速、用 key 做有限的重复检测"。chunk / bin / tcache / next / key 这五个概念串起来，malloc 和 free 的全部路径就都说得通了。再看故障手册里的 double free，就只是在问：这条链什么时候、因为什么被搞乱了。
