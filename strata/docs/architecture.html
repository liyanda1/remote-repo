0 · 这是什么形态的产物

它不是 agent，是一套工程：四个部件各管一件事，由一个 Python 工具链串起来。 你可以只装其中一部分——只查不建，就只连一个 MCP 服务端的地址，不装任何脚本。

图 1　四个部件：skill 管流程，command 管触发，MCP 管取数，卡片与索引是数据
部件形态职责放在哪
Skill
skill		 SKILL.md 构建知识库的完整工作流。模型加载后知道：先自检、再抽取、怎么编译、怎么写卡片、 什么情况必须停下来问人。 .opencode/skills/strata/
Commands
command		 *.md 七个斜杠命令，其中 /strata-build 一条走完整条建库链。 每个命令里嵌了 shell 块，敲命令时脚本先跑，输出直接进模型上下文—— 你不需要手动敲 python。 .opencode/commands/
MCP Server
mcp		 stdio / HTTP 查询层，六个语义化工具 + 一个全景图页面。可以 stdio 本机拉起，也可以 HTTP 常驻让全组远端连—— 一份索引一个服务端，浏览器开服务地址就能直接看图。 strata.py serve
数据 Markdown + SQLite 卡片是事实源（进 Git、可 review），索引是派生物（可删可重建）。 cards/ + index.sqlite

为什么不做成 agent

agent 有自己的推理循环，会自己决定下一步做什么——这在建知识库时恰恰是风险： 它会自由发挥、跳跃步骤、把「可能」写成「确定」。这里需要的是相反的属性。

需求agent 的问题本方案的对应物
流程必须固定agent 可能跳过编译直接下结论skill 把步骤写死，每步有验收
证据必须可查agent 会说「我记得」MCP 工具返回带 provenance 的边
越权必须不可能靠 prompt 约束，能绕status 闸门：模型写不进 confirmed
操作要省事要对话几十轮command 一条命令跑完一串脚本
一句话分工 skill 管流程（先做什么后做什么）、command 管触发（一条命令跑完一步）、 MCP 管取数（结论从库里查，不靠记忆）、模型只做语义判断（这段代码属于哪个功能点、 这个用例验证的是哪个场景）。凡是能算的，一律不给模型留发挥空间。

1.3 四层：场景 · 功能 · IT/UT · 实现

四个槽位是语义角色，不是四张表。领域差异全部下沉到领域包， 内核只认槽位、边、空洞和查询接口。

图 3　四个槽位构成业务轴，实现层向外连出依赖轴；两轴交于代码层
槽位通用层名 语义角色 不同领域里的实际形态（示例）规模
intent场景层人要达成什么 一次整车升级 / 一次 ECU 刷写 / 这个库承诺的一项能力十到百
mechanism功能层 一个场景由哪几个功能点实现（1 : N，不是一对一） 状态机 + 断电恢复 + 完整性校验 / 会话建立 + 服务分发 + 结果上报 / 一个功能模块百到千
verification验证层 怎么证明这些功能点成立。全部是 IT / UT，两者只是粒度不同 IT：端到端升级、断电恢复；UT：状态机单测、诊断用例。 载体可能是 gtest、pytest、诊断脚本或 HIL，但都属于 IT/UT千
implementation实现层代码实体 符号 / 组件 —— 唯一一层与领域完全无关万级

这张表只是示例，不是规范。内核不认识「状态机」，也不认识「gtest」， 它只认四个槽位名。具体某一层装什么、字段叫什么，由领域包决定： OTA 可以把功能点定成「状态 + 事件」，诊断可以定成「序列号 + 服务」，通用 C++ 库可以定成「模块」。 换领域只换包，不动内核，也不改这张表的语义——变的只是右列的例子。

两个容易搞错的点 功能层不是「一层就一个功能」。一个场景通常拆成 3–10 个功能点， 场景与功能点是 1 : N，composed_of 边上用 weight 表示覆盖程度， 所以「部分覆盖」也能如实表达。

验证层不按测试框架分类。按 gtest / pytest / 诊断脚本分，等于把工具链焊进模型， 团队一换框架整个库就得重建。正确划分只有一条线：这条用例是 IT 还是 UT， 框架、语言、跑在台架上还是本机，都只是它的载体。

关系分两类，性质完全不同，必须都建在同一个图里：

关系方向回答什么数据来源
业务轴代码 ← 用例 ← 功能点 ← 场景改了这段代码，影响什么业务本仓内即可闭环
依赖轴组件 ↔ 组件、符号 ↔ 符号改了这个导出符号，谁要重新验证构建产物（ELF）、契约声明
精度在某一层必须截断 端到端 IT 一次能触及上千个符号。如果它和 UT 一样下钻到函数级， 「改了 A 影响什么」的答案会变成「影响全部」，影响面立刻失去意义。 正确做法：IT 聚合到组件/接口级，UT 才下钻到符号级，边上带 weight 表示覆盖强度。

2 · 数据模型

2.1 五种边

边是这套系统全部价值的载体。判断一条边能不能入库，只问一句：它凭什么存在？

边方向含义生成方式默认置信度
composed_ofintent → mechanism场景由哪几个功能点拼成人工 / 模型提议 + 审核确定
verified_bymechanism → verification功能点由哪些用例验证解析测试结构 / 被测符号归属确定
exercisesverification → implementation用例执行了哪些代码覆盖率报告（首选）/ 调用匹配确定 / 很可能
depends_onimplementation → implementation调用 / 引用 / 继承AST、ELF 符号交叉确定
fulfillsintent → intent跨领域串联人工声明确定

边方向由内核强校验：写反了直接报错，不会静默入库。 代价极小的一个约束，拦下的却是一整类错误——实测中 verified_by 方向写反， 1349 条边被整批拒绝，没有校验的话这批错边会一直躺着到有人发现查不出东西。

2.2 证据账本

每条边必须带四个字段，缺一个就是 H4 致命空洞：

字段取值作用
source_typeextractor / manual / user-answer / llm-proposal这条知识谁产生的
source_reffile:line / report-id / conversation-id回哪里核对
confidencecertain / likely / possible结论档位，查询时分组
evidence一条能验证的原文或位置审计时唯一靠得住的东西
来源默认置信度理由
覆盖率、符号表、AST（可复现）确定跑一遍就能验证
启发式匹配（按名字、按 include）很可能有依据，但可能漏或串
人工填写确定人对自己写的东西负责
用户问答补全很可能口述可能记错，需代码印证
模型提议可能必须人确认才能升档

正文：这个用例验证 format_to 在基础类型上的输出，
包括空容器、超长字符串、格式化串复用三种情况。
部分谁读作用
frontmatter.links编译器边，唯一可信的连接来源
frontmatter 其余字段查询层决定这条知识能不能被信任、怎么分组

正文里的 [[双链]]模型路标；编译器忽略，避免重复计边

2.4 状态闸门

状态含义谁能置为查询时
draft草稿模型不返回
proposed模型认为可以了模型单独成组，标「未确认」
confirmed人确认，或有机器证据人或抽取器正常返回
disputed发现矛盾任何人返回并标冲突

模型的产出上限是 proposed。这条规则比任何 prompt 约束都硬： 即使模型判断错了，错的也只是「未确认」那一组，不会污染结论。

3 · 构建：用命令，不用手动敲脚本

建库的全部操作是几条斜杠命令。每个命令内部嵌了 shell 块，OpenCode 在提交提示词之前 先把脚本跑掉，把真实输出塞进模型上下文——所以模型看到的是库里的实际情况， 而不是它以为的情况。第一次建库只需要一条 /strata-build。

3.1 安装（三步，不需要配环境变量）

# 1) 依赖：只有一个 PyYAML，其余是 Python 标准库。全流程离线
pip install pyyaml

# 2) 把 skill 和命令复制到你的代码仓（在代码仓根目录执行）
cp -r /path/to/strata/.opencode/skills/strata  .opencode/skills/
cp -r /path/to/strata/.opencode/commands       .opencode/commands/

# 3) 指定知识库工程在哪 —— 二选一，都不用碰 shell profile
#    a. 写一次配置（推荐）：之后所有命令都不用再带路径
python .opencode/skills/strata/scripts/strata-run.py home set /path/to/strata
#    b. 临时试：命令里直接带 --home，什么配置都不写
#    /strata-build /path/to/你的代码仓 --home /path/to/strata

定位工程根有四种方式，优先级从高到低。命令行参数永远排第一—— 因为环境变量和配置文件都会过期，换个仓、换个人、换台机器就指错地方了：

方式写法什么时候用
命令带目录 /strata-build ./repo --home /path/to/strata 临时试一下、或一次性的仓
仓内配置 home set <路径> → 写进 .opencode/strata.home 日常开发，写一次管很久
环境变量 export STRATA_HOME=/path/to/strata CI / 容器，进程级、跟着流水线走
skill 自身位置 skill 装在工程内部时自动命中 在知识库工程里自己调试
为什么不再要求配环境变量 环境变量是进程级的：新开一个终端就没了，换个人登录同一台机器也没了， 而它指向的目录恰恰是团队共享的。写进 .opencode/strata.home 的路径 跟着仓库走，谁 clone 谁生效；命令里带 --home 则完全无状态，跑完不留痕。 环境变量保留给 CI，因为那里恰好需要一个外部注入的变量。
找不到工程根时不要猜路径 四种方式都没命中时，脚本会列出「仓内配置 / 环境变量 / skill 位置」各自解析到什么， 然后报错退出，不会静默写到一个莫名其妙的目录。这是刻意的：宁可失败，也不能写错地方。

3.2 一条主线 + 六个零件

图 5　七个命令：build 是一条主线，剩下六个是它能被单独调用的零件
命令什么时候用它内部跑了什么
/strata-build第一次建库，只敲这一条 依次驱动下面三步，每步之间把真实输出给你看，需要裁决时才停下问你
/strata-init想单独重跑抽取where → extract → compile， 然后模型读文档播种场景卡
/strata-extract代码大改之后extract → compile → holes， 模型对比前后数字找异常
/strata-impact每次动代码之前git diff --stat → impact-diff， 模型按三档汇报并给必跑测试清单
/strata-fill每周治理holes → 逐条提问 → 改卡片 → compile
/strata-review模型播种之后drafts → 逐张裁决 → compile
/strata-status想看库健不健康where + stat + holes
为什么不用记顺序 每条命令的最后都跑一次 strata-run.py next，它按库的真实状态判断下一条该干什么： 有草稿 → 让你 review；有致命空洞 → 让你 fill；都没有 → 告诉你库能用了。 这个判断由脚本做，不由模型猜，所以不会出现「刚建完就让你去补一个不存在的空洞」。

3.3 第一次建库：跑起来是什么样

第一步 · 抽取与编译（/strata-build 的前三个 shell 块）：

$ python .opencode/skills/strata/scripts/strata-run.py where
Strata 自检
==========================================================
工程根      /path/to/strata
索引        /path/to/strata/index.sqlite  不存在
卡片文件    0
领域包      generic-cpp

$ python .opencode/skills/strata/scripts/strata-run.py extract .
抽取完成  模块 16  符号 776  用例 683  能力 31
边         verified_by 1010  exercises 793  composed_of 20

$ python .opencode/skills/strata/scripts/strata-run.py compile
按槽位:   implementation=776  intent=31  mechanism=16  verification=683
按边类型: composed_of=20  verified_by=1010  exercises=793
按置信度: certain=792  possible=31  likely=683

校验通过，无错误无警告。

模型接着会把这三个分布念给你听，并抽一张用例卡去核对行号——因为证据链不可复核的话， 整个库都不可信。这一步是强制的。

第二步 · 播种场景（模型的主力工作）。它读你指定的文档，一次产出不超过 12 张草稿卡：

---
id: ota.scn.power-loss-recovery
slot: intent
domain: ota
title: 刷写中断电后恢复
status: draft                    # 只能是 draft
confidence: possible               # 没有代码证据支撑
source: llm-proposal
links:
  - { to: ota.tr.flashing-power-lost, type: composed_of, weight: 1.0 }
evidence:
  - { ref: "docs/upgrade-spec.md#42", note: "文档明确要求回滚" }
---

第三步 · 裁决（/strata-build 自动进入这一步）。模型逐张汇报， 你只需要说「确认 / 改 / 删」。确认后 status 变 confirmed，重新编译即被查询采纳。

第四步 · 交接。每步收尾都会跑一次状态判断，输出长这样，模型必须照它告诉你下一条命令：

$ python .opencode/skills/strata/scripts/strata-run.py next
当前状态
==========================================================
  intent=31  mechanism=16  verification=683  implementation=776  合计 1506
  待裁决 intent=31

下一步：/strata-review
原因  ：有 31 张草稿没裁决（intent 31 张）。
之后  ：/strata-fill 补结构空洞。

这就是「流程连贯」的全部机制：不需要你记住七条命令的先后，也不需要模型自由发挥判断该干嘛—— 下一步由库的真实状态决定，换个仓、换个阶段，答案自动变。

为什么一次只播 12 张 批量生成几百张「语义漂亮但挂不上任何代码」的卡片，是这类系统最常见的死法—— 你会在两周里手工接线，然后放弃。小批量 + 逐条 review，用户能看完、能纠错， 这才是知识库能长期活下去的原因。

3.4 三方分工

角色只做这些绝不能做
脚本解析卡片、建索引、遍历、校验、扫洞任何语义判断
模型读文档、提议场景、连边、按模板提问、解释查询结果写 confirmed、编造场景、绕过校验
人裁决草稿、回答空洞、决定领域包的功能粒度手工维护上万条符号边

4 · 使用：一套服务端，全组共用

建库的人用 skill，查库的人只需要一个 URL。这是两种接入，不是两种权限： 索引只有一份，服务端只有一个，全组通过远端 MCP 连过来查同一份数据。

4.1 部署形态

图 6　部署形态：建库机写、服务端读、全组用；三者的唯一契约是同一个 index.sqlite

不要每人拷一份 index.sqlite。这个方案在两周内就会崩： 五个人各拷一份，各自跑一次 extract，五个库的节点数就开始不一样， 两个月后没人说得清「改了 format_to 影响 54 个用例」这个结论是哪份库跑出来的。 正确做法是把「库」当成团队的一份共享资产，像 Git 仓库一样只有一份正本。

在建库机上起服务（这台机器有卡片和索引的写权限）：

# 基本用法：监听所有网卡，带一个组内口令
python strata.py serve --http --host 0.0.0.0 --port 8760 --token <组内约定口令>

# 自检：返回节点数、边数、最近一次编译时间
curl http://10.0.0.21:8760/healthz
{"ok": true, "nodes": 1506, "edges": 1823, "compiled_at": "2026-11-08T23:01:37+0800"}
参数作用不设会怎样
--http走 Streamable HTTP 传输，远端可连 退回 stdio，只能本机拉起子进程用
--host监听地址，团队用就写 0.0.0.0 只监听 127.0.0.1，别人连不进来
--port端口，默认 8760—
--token要求 Authorization: Bearer <token> 任何能访问该端口的人都能查（内网也建议设，防误连）
--db指定索引路径用工程自带的 index.sqlite

常驻方面没有魔法：Linux 上包一个 systemd 单元，Windows 上用任务计划（开机启动、 失败重启）。服务端是纯 Python 标准库实现，不依赖 Node、不依赖任何外部服务， 内网离线环境可以直接跑。

[很可能影响]  54 条

AI 应该这样转述（这就是它该给你的回答，不是它实际会自由发挥的版本）：

改了 format_to 函数体，影响面分三档：

· 确定影响 0 条 —— 当前没接覆盖率报告，所以用例→代码这层全是静态匹配，
  进不了确定档。这是已知限制，不是「没问题」。
· 很可能影响 54 条 —— 9 个模块 + 45 个用例，其中直接相关的是
  base_test.format_to、format_test.format_int 等 45 个用例。
· 可能影响 14 条 —— 上层能力，说明 format_to 是公共 API 的一部分。

必跑测试建议（前三个最关键）：
  ./build/test/base-test --gtest_filter=base_test.format_to
  ./build/test/format-test --gtest_filter=format_test.format_int
  ...

结论：这是公共 API 的内部实现改动，影响面在用例层铺得比较开，
建议至少跑 base-test 与 format-test 两个二进制。

4.4 多人共用的四条硬约束

「多人连同一个服务端」听着简单，实际会踩四个坑。这套实现在代码层面各自做了处理：

约束实现为什么必须这样
查询不可能写坏库 服务端用 mode=ro 打开索引，并设 PRAGMA query_only 靠调用方自觉是挡不住的。文件层只读 + 连接层只读，双保险， 即使工具实现里误写了 INSERT 也会被 SQLite 直接拒绝
重编不留空窗 整个重建在一个事务里：DELETE + INSERT 一起提交 否则重编的几十毫秒里有人来查，会拿到「0 个节点」， 然后开始怀疑库坏了
坏卡片不拖垮共享库 编译有错误就整体 ROLLBACK 一个人写错一张卡，不该让全组的库变成半成品。 他的编译失败，别人继续查上一版
重编后不用重启服务 每个请求开一个只读连接，用完即关 常驻连接会一直抓着旧的索引文件句柄， 重建完还在返回一个月前的数据，且没人会想到要重启
鉴权做到什么程度够用 内网团队用 Bearer token 足够：它的作用不是防攻击，而是防「隔壁组误连了你的库、 拿着别人的结论去评审」。真要按人分权限，再在前面挂一层反向代理做 SSO， 服务端本身不需要改——它只认 Authorization 头。
远程模式下的两个已知限制 1. 会话不持久：会话表在内存里，服务重启后客户端会收到 404 并自动重新 initialize，不用手动干预，但也别指望它记住上下文。
2. log_gap 只写 gaps.jsonl：远端连的是只读索引， 写不进库。缺口会落到 jsonl，等建库机下一次 compile 时回放进库—— 所以「登记了但列表里暂时看不到」是正常的，不是丢了。

4.5 为什么回答必须带档位

开发者看到「确定 3 条、很可能 5 条、可能 12 条」，会自己判断该信多少； 看到混在一起的 20 条，一次就不再打开了。信任靠分级建立，不靠准确率。

所以规则写死在两处：服务端 initialize 返回的 instructions，以及仓库里的 AGENTS.md：

## Strata 知识库使用规则

- 回答「改这个会不会影响 X」「这个场景怎么处理」之前，**先调 strata 查询**，不许凭印象答。
- 查询结果分三档：确定 / 很可能 / 可能。转述时**必须保留档位，不许合并**。
- 查不到就调 log_gap 登记并向用户提问，**不许编造场景、假设阈值、推测文件名**。
- 引用代码位置只能来自证据链，不许自行补全路径或行号。
